# FR-03 로봇암 A: 에디터에서 "적용"을 누르면 A-1 집기에서 멈춘다 (헤드리스 시험은 통과)

> 작성일: 2026-11-02 · 브랜치: `feature/pw-kitting-physical-place`
> 범위: Unity 에디터에서 주문을 적용하면 로봇암 A가 선반 칸 A-1에서 물건을 집지 못하고 `Fault`로 멈추는 문제. 헤드리스 E2E 시험은 같은 코드로 통과한다
> 표시: **확정**(측정으로 확인) · **추정**(코드나 정황으로 본 것) · **미검증**(아직 확인하지 않음)

## 0. 한 줄 요약

시험은 프레임마다 시간을 0.02초로 고정해서 돌리고 에디터는 그렇지 않다. 프레임 간격이 물리 간격(0.02초)보다 길면 집기의 마지막 단계(`물건 위치로 팔 뻗기`)에서 j2 관절이 목표보다 1.6° 모자란 채 멈추고, 허용 오차(1.5°)를 0.1° 넘어 실패한다. 허용 오차를 3°로 늘려 시험에서는 모두 통과했다. **무엇이 j2를 막는지는 아직 모른다.**

## 1. 증상 (확정)

에디터 로그(`Logs/Editor.log`)에 이렇게 남고, 키팅이 거기서 끝나 박스로 가지 않는다.

```
KittingStation: 키팅이 Fault로 끝났다. 선반 칸 A-1에서 집지 못했다. 물건 위치로 팔 뻗기:
팔이 시간 안에 알려 준 관절 각도에 닿지 못했다(무언가에 걸렸거나 너무 느림)
```

- 전날 에디터 로그(`Logs/Editor-prev.log`, 11/1)에도 A-1 집기 `Fault`가 6번 있다. 이번에 새로 생긴 문제가 아니다.
- 이 문구 뒤에 "관절 N 목표 … 현재 …" 상세가 붙지 않으면 모든 관절이 목표에서 5° 이내라는 뜻이다(`TransferDiagnostics.JointDeviation`).

## 2. 왜 시험에서는 안 보였나 (확정)

`KittingEndToEndTests`는 시작할 때 `Time.captureFramerate = 50`을 건다. 프레임 하나가 정확히 물리 스텝 하나(0.02초)가 된다. 에디터는 프레임 시간이 매번 다르다. 지금까지 "시험 통과"를 에디터 동작으로 읽었지만 둘은 다른 조건이다.

환경 변수로 시험의 시간 흐름을 바꿔 에디터 조건을 헤드리스에서 재현할 수 있다(`FrameTimingSettings`).

| 환경 변수 | 뜻 |
|---|---|
| `MEDIKIT_E2E_CAPTURE_FPS` | 프레임 고정 fps. 기본 50. 0이면 고정하지 않는다 |
| `MEDIKIT_E2E_TARGET_FPS` | 프레임 수 상한. 기본 0(제한 없음). 양수면 수직 동기화를 끄고 그 값으로 제한 |

## 3. 측정 (A행 단독 시험, 같은 코드와 씬)

고치기 전(허용 오차 1.5°):

| 조건 | 결과 |
|---|---|
| 프레임 고정 50fps | 통과 (3번) |
| 고정 끔 + 상한 없음 | 통과 (2번) |
| 고정 끔 + 30fps | **실패 (4번)**, 시뮬레이션 약 15.5초에 중단 |
| 고정 끔 + 10fps | **실패 (3번)**, 시뮬레이션 약 17.3초에 중단 |

- 실패한 실행은 모두 같은 모습이다: 팔이 약 6초부터 멈춰 있고 j2(`upperarm_Link`)만 목표 59.7°에 현재 61.3°로 -1.6°, 나머지 관절은 0.2° 이내. 허용 오차는 `_jointToleranceDeg` 1.5° (`ArmItemTransfer`, 씬에 직렬화) (확정).
- 같은 7번째 후보로 집는 통과 실행은 j2가 -29.3°에서, 실패 실행은 -28.7°에서 멈춘다. 같은 목표인데 멈추는 곳이 0.6° 달라진다 (확정). **어딘가에 걸려 멈추고 그 위치가 프레임 타이밍에 따라 달라진다** (추정).
- 겹침 조회에 `finger_link1_0`(레이어 Arm) ↔ `Shelf_A-1/Floor`(레이어 Default)가 나온다. 그런데 손가락 아래끝(y 0.571)이 바닥 윗면(y 0.566)보다 5mm 위라서 바닥에 눌렸는지는 **미검증**이다.

## 4. 시도했지만 해결하지 못한 것 (둘 다 되돌렸다)

| 시도 | 가설 | 결과 |
|---|---|---|
| `ArmA.prefab`의 베이스 도착 허용 오차 `_arriveToleranceM` 2cm → 1mm | 베이스가 서는 자리가 프레임 간격에 따라 0.6~1cm 달라져 집기 후보가 3번째에서 7번째로 바뀐다 | 네 조건 모두 서는 자리(x 2.703)와 후보(7번째)가 같아졌지만 30fps와 10fps는 그대로 실패. 가설 틀림 |
| 손가락 끝과 바닥 사이 여유 5mm를 겨냥 높이에 추가 (`GraspLift`) | 손가락 끝이 정확히 바닥면 높이에 닿아 눌린다 | 쥐는 자리 높이가 `0.689→0.609m`로 같았다. 보정 한계 8cm(`_maxShiftM`)에 걸려 최종 높이가 이미 정해지므로 겨냥을 올려도 실제 목표가 안 바뀐다. 검증 못 함 |

참고: 로그마다 "쥐는 자리가 물건에서 +8.0cm 벗어남, 한계 8.0cm까지만"이 찍힌다. 알려 준 쥐는 자리가 지금 물건보다 약 11cm 높다. 선반이 바뀐 뒤 A행 자세를 다시 가르치지 않았을 수 있다 (추정).

## 5. 한 고침 (증상 쪽)

`Scene_Cell.unity` 한 줄: `_jointToleranceDeg: 1.5` → `3`. 알려 준 관절 각도로 쥐는 자리에 갈 때 허용하는 관절 오차다. 지나가는 자리(`_travelJointToleranceDeg` 4°)보다는 작게 두었다.

고친 뒤(허용 오차 3°) 모두 통과했고 튕김은 0개였다.

| 시험 | 조건 | 결과 |
|---|---|---|
| A행 | 30fps | 키트 완료, 시뮬레이션 70.1초 |
| A행 | 10fps | 키트 완료, 128.8초 |
| A행 | 고정 끔 + 상한 없음 | 키트 완료, 64.7초 |
| A행 | 프레임 고정 50fps | 키트 완료, 64.0초 |
| B행 | 30fps | 키트 완료, 140.6초 |
| C행 | 30fps | 키트 완료, 142.5초 |

**한계:**

- 판정만 완화한 것이라 원인(무엇이 j2를 막는지)은 그대로다 (미검증).
- 각 조건 1번씩만 돌렸다. B행, C행은 30fps 한 번이다.
- **에디터에서 직접 눌러 확인한 것이 아니다.** 헤드리스에서 에디터 조건을 흉내 낸 결과다. 에디터 화면(데모 패널, 도구 카메라 렌더링)은 흉내 내지 못했다.
- 팔이 목표에서 1.6° 모자란 채 쥔다. 도구 끝점이 얼마나 어긋나는지는 재지 않았다. 통과한 시험에서는 이후 쥐기와 놓기가 모두 끝났다.
- 놓을 때 튕김, 슬롯 4 내리기 시간 초과 등 다른 알려진 문제와는 상관이 없고 그대로 남아 있다.

## 6. 다음에 할 일

1. 에디터에서 "적용"을 눌러 A/B/C행이 끝까지 가는지 직접 본다 (가장 먼저).
2. 무엇이 j2를 막는지 찾는다. 팔이 멈춘 순간 겹치는 충돌체를 접촉점으로 확인하고(링크에 `OnCollision*`을 달지 않는다), 멈추는 위치가 프레임 타이밍에 따라 달라지는 이유를 본다.
3. A행 가르친 자세를 다시 가르쳐 보정 한계(8cm)에 걸리지 않게 한다.
4. 판정을 3°로 둔 채 쥐는 정밀도에 문제가 없는지 도구 끝점 어긋남을 잰다.
