## 1. 학습 이미지와 씬 이미지의 촬영 조건 차이: 카메라, 그림자, 조명 색 (11-02, 11-03)

CNN은 이미지만 보므로, 학습한 합성 이미지와 씬에서 찍은 이미지의 조건이 다르면 오프라인 점수와 상관없이 틀린다. 이 차이를 세 번에 걸쳐 찾아 고쳤다. 앞의 둘은 11-02에, 마지막 둘은 11-03에 나왔다.

### 1-1. 카메라 위치, 가림, 그림자, 비균일 스케일 (11-02)

**증상**: 샘플 박스를 촬영한 `InspectionCaptures/…/full.png`가 박스를 제대로 보여 주지 못했다. 카메라가 검사 구역 위가 아니라 씬 레이아웃용 `Camera` 큐브 위치에 있었고, 박스 위로 어두운 대각선 띠와 구성품 위 그림자가 보였다.

**원인과 조치**

| 원인 | 조치 |
|---|---|
| `Camera` 큐브가 y=1.05라 박스 위 0.14m밖에 안 됨(설정은 박스 중심 위 0.6m, y=1.51) | `Camera` 오브젝트를 y=1.51로 올리고 `InspectionCameraRig`를 붙임. `Beam`, `Camera` 큐브는 지우지 않고 재사용 |
| `Beam`이 y=1.2에서 시야를 가림(박스 면 기준 ±0.077m를 덮어 슬롯 2, 3이 통째로 가려짐) | y≥1.6으로 올리거나 지움 |
| 큐브나 `Beam`이 방향성 조명 아래 박스 위에 그림자를 드리움(학습 이미지에는 그림자가 없음) | 두 오브젝트의 `Cast Shadows`를 Off |
| `Camera` 큐브가 (0.2, 0.15, 0.2) 비균일 스케일인데 렌더 카메라가 그 자식으로 만들어져 스케일을 상속함 | 렌더 카메라가 부모 스케일을 상속하지 않도록 코드 수정 |
| 씬의 방향성 조명이 박스에 그림자를 드리움 | `InspectionCameraRig`의 카메라에서만 그림자를 끔(URP 카메라별 `renderShadows = false`) |

### 1-2. 실제 씬에서 거즈를 붕대로 오분류: 조명 색 차이 (11-03)

**증상**
- 학습과 오프라인 평가는 NFR-04를 통과했는데(박스 정확도와 불량 재현율 각 0.90 이상), Unity 씬에서 정상 박스를 검사하자 슬롯 1의 `gauze`를 `bandage`(신뢰도 0.89)로 판정해 불량으로 처리했다.
- 검사 결과는 `Cnn`이었고 규칙 판정으로 대체된 것이 아니었다.

**원인 (확정)**
- 학습 이미지의 조명은 흰색이었고, 씬의 Directional Light는 따뜻한 색 `(1, 0.957, 0.839)`이었다. 색이 단서인 구성품(거즈, 붕대)에서 이 차이가 오분류로 이어졌다.
- 크롭의 평균 색을 학습 이미지와 씬 이미지에서 비교해 차이를 수치로 확인했고, 수정 뒤에 다시 비교했다.

**해결**
- 합성 데이터 생성기에 **조명 색의 따뜻함 랜덤화**(`LightWarmthDeviation`)를 추가했다. 흰색부터 씬의 따뜻한 조명까지 흔든다.
- 새 난수가 다른 값(위치, 각도 등)을 바꾸지 않도록 변이에서 **마지막에** 뽑는다. 같은 시드의 기존 데이터는 같은 결과를 유지한다.
- 새 데이터셋(`20261103_111643`)으로 재학습했다(`runs/20261103-111741`, 최고 에폭 19). 씬에서 정상 박스를 다시 검사해 해소되는 것을 확인했다.
- 어떤 슬롯이 왜 불량인지 알 수 있도록 `CnnSlotJudge`가 불일치 슬롯마다 기대 값, 예측 값, 신뢰도를 로그로 남기게 했다.

### 1-3. 조명 틴트를 넣었더니 데이터가 너무 밝음 (11-03)

**증상**: 첫 번째로 만든 데이터셋(`20261103_111218`)이 과하게 밝았다(거즈 평균 밝기 254).

**원인 (확정)**: 미리보기 조명(`PreviewRenderUtility`)의 기본 색은 흰색이 아니라 회색(약 0.77)인데, 틴트를 그 색을 **대체**하는 값으로 넣어 밝기가 올라갔다.

**해결**: 틴트를 캐시해 둔 기본 조명 색에 **곱한다**(`key.color = baseColor * tint`). 새 데이터셋(`20261103_111643`)을 만들고 이전 폴더는 버렸다. 1-2의 재학습은 이 값으로 했다.

### 배운 점
- 학습 이미지와 판정 이미지의 조건(카메라 높이와 시야, 그림자, 배경색, 조명 색, 밝기)을 맞추는 것이 모델 성능보다 먼저다. 1-1의 그림자와 시야를 맞춘 것이 1-2의 조명 색 문제를 따로 볼 수 있게 한 선행 조건이었다.
- 합성 데이터의 랜덤화 목록에는 "실제 씬이 그 값에서 벗어나 있는 정도"가 들어가야 한다. 오프라인 통과는 같은 분포 안의 점수이고, 씬에서의 검증은 별도로 필요하다.
- 검사 결과의 `Verdict.Method`가 `Cnn`인지 먼저 본다. 규칙 판정 대체와 CNN 오분류는 원인이 다르다.
- 데이터를 새로 만든 뒤에는 클래스별 평균 밝기와 색을 한 번 확인한다(1-3은 이 확인으로 잡았다).

## 2. 위치·각도 흔들림을 키우면 오경보가 늘어남 (11-03)

### 배경
- 샘플 박스는 위치와 방향이 늘 같다. 같은 조건(키트, 변형, 슬롯, 오구성 품목)이면 같은 이미지가 나와서, 200개를 재도 서로 다른 이미지는 훨씬 적다. 실제로 신뢰도 0.486이 같은 박스에서 4번 똑같이 나왔다.
- 그래서 흔들림이 없는 측정은 "학습 때와 같은 조건에서는 맞는다"까지만 보여 준다. 실제 키팅은 박스와 구성품 위치가 조금씩 다르다.

### 측정 방법
- `InspectionSampleSpawner`에 흔들림 배율 `_jitterScale`을 추가했다. 박스 위치와 방향, 구성품 위치와 방향을 균일 분포로 흔든다. 배율 1은 학습 랜덤화 범위의 끝(박스 ±1cm와 ±5도, 구성품 ±6mm와 ±20도), 배율 2는 그 두 배다. 배율 0이면 난수를 쓰지 않아 이전 박스와 같다.
- `InspectionBenchmark`가 박스 200개(불량 92: 누락과 오구성 절반씩, 시드 20261103)를 만들어 판정과 정답을 비교한다. 측정이 끝나면 스포너의 원래 배율로 되돌린다.
- 두 컴포넌트에 `_jitterScale` 필드가 있지만, `Run Benchmark`로 측정할 때는 Benchmark 쪽 값만 쓰인다(측정 시작 때 스포너 값을 덮어쓴다). 스포너 쪽 값은 메뉴로 박스를 하나씩 만들 때만 쓰인다.

- 모델은 학습한 범위 안의 위치·각도 편차는 견디고(배율 1 통과), 그 밖으로 나가면 불량을 놓치기보다 "뭔가 다르다"를 불량으로 몰아가는 쪽으로 무너진다. 안전 측 실패이지만 정상 박스가 불량으로 나가면 처리 비용이 든다. (추정)
- 배율 1에서도 오경보 2건이 있어 학습 범위 끝에서는 여유가 거의 없다. 실제 키팅 편차가 학습 범위(박스 ±1cm, 구성품 ±6mm)를 넘을 수 있다면 이 모델은 위험하다.
- 박스 흔들림과 구성품 흔들림을 한꺼번에 키웠으므로 어느 쪽이 더 영향이 큰지는 모른다(미검증).

### 결정과 다음 단계
- 실제 키팅 편차를 알기 전에는 학습 범위를 넓히지 않고 현 상태를 유지한다(측정과 한계만 기록).
- 선택지는 세 가지였다: A. 위치·각도 범위를 넓혀 데이터를 다시 만들고 재학습한 뒤 배율 1, 2, 3으로 재측정(범위를 넓히면 정밀도가 떨어질 수 있어 재측정이 전제), B. 키팅 쪽의 실제 편차를 확인한 뒤 범위를 정함, C. 현 상태 유지(선택).
- 키팅이 붙은 뒤 같은 도구로 다시 재고, 오경보가 늘면 A 또는 B로 간다. A로 갈 때는 박스와 구성품 흔들림을 따로 키운 측정을 먼저 해서 어느 범위를 넓힐지 정한다.
- 결과 요약 표는 `MLTraining/README.md` 5장에도 있다.

## 3. 실제 키팅 결과를 CNN이 키트 3개 모두 불량으로 판정 (11-03~04)

### 증상
- 11-03 22:14, 그래픽을 켠(`-nographics` 없이) `FullProcessTests`에서 키트 3개가 모두 불량통으로 갔다(`[RejectBin] LOT-0001~0003`). 기대는 2개 출하, 1개 불량이다.
- 촬영 이미지(`InspectionCaptures/20261103-221508/LOT-000N/`)는 방향과 크롭이 정상이었다. CNN이 틀렸다: 거즈→`test_cassette`(0.83~0.87), 소독제→`blood_tube`(0.84~0.90), 붕대→`swab`(0.67~0.73). 크롭 12장의 슬롯 정확도가 4/12였다.
- 같은 시험이 헤드리스(`-nographics`)에서 통과한 것은 `InspectionCameraRig.CanRender`가 false라 규칙 판정(슬롯 센서)으로 대체되어서다. CNN은 한 번도 쓰이지 않았다. 1장의 "배운 점"대로 `Verdict.Method`를 먼저 봐야 한다.
- 이때 합성 테스트(NFR-04)는 통과 상태였다. 합성 점수가 좋아도 씬 이미지에서 틀리는 것은 2장과 같은 종류의 문제다.

### 좁힌 방법
추측으로 가설을 세우면 네 번 중 세 번 틀렸다. 아래 순서로 측정해서 좁혔다.
1. **이미지를 먼저 본다.** 크롭이 슬롯에 맞는지, 방향이 맞는지.
2. **씬 이미지로 채점한다.** 실제 키팅 크롭 12장과, 씬의 `InspectionBenchmark`가 만든 샘플 박스 49개(정상·누락, 정답을 안다)로 기존 모델과 새 모델을 나란히 비교한다. 합성 테스트 점수는 보지 않는다. (비교는 저장소 밖 임시 스크립트로 했다.)
3. **가림 실험.** 틀린 크롭의 일부를 바닥색으로 덮고 확률이 어떻게 바뀌는지 본다. 모델이 어디를 보고 그렇게 읽는지 직접 나온다.
4. **광원을 하나씩만 켠 렌더.** 환경광, 주광, 보조광을 따로 켜서 밝기가 어디서 오는지 가른다.
5. **같은 박스를 씬과 합성에서 같은 위치로 비교한다.** 바닥, 벽 안쪽 네 면, 벽 윗면의 평균 밝기를 표로 만든다.

- **원인 사슬**

- **채택한 값**: `SyntheticLighting.Default` = 환경광 (0.30, 0.30, 0.315), 주광 1.75, 보조광 0. 씬에는 보조광이 없다. 여섯 위치가 씬의 0.90~1.01배다.
- 박스 밖 배경색도 달랐다. 씬 샘플 12장의 모서리 평균은 밝기 45~58(어두운 컨베이어)인데 합성은 푸른 회색(115~128)이라, 박스가 어긋난 크롭 가장자리에 보였다. 검사 카메라와 합성이 같은 값(`InspectionBackground.Color`)을 쓰게 했다.
- 조명 방향은 씬 Directional Light와 같은 yaw −30°, pitch 50°를 기준으로 하고 ±25°, ±10° 흔든다. 검사 카메라는 이미지 위쪽을 박스의 +Z에 맞춰 찍으므로 박스 기준 조명 방향이 거의 고정이다. 씬 사진에서 위 벽 안쪽은 밝고 아래·오른쪽 벽 안쪽은 어두운 것이 이 방향과 맞는다.

**3-4 (확정)**: `SyntheticVariation`이 눕는 확률에 걸린 슬롯의 서 있을 때 각도(±20°)를 눕는 각도(±90°)로 덮어썼고, 렌더러는 원기둥이 아닌 구성품에도 그 각도를 그대로 썼다. 직사각형이 임의 각도로 놓인 학습 이미지가 대부분이 되어, 가로로 놓인 씬의 `test_cassette`(샘플 10장 전부 같은 자세)를 거즈로 읽었다. 눕는 각도를 `GetItemLyingYawDegrees`로 따로 두고, 렌더러가 눕는 원기둥에만 쓰게 했다. 고치기 전 3-3까지 맞춘 모델은 빈 슬롯 오류가 0건이 됐지만 이 오류가 새로 드러나 샘플 박스가 43/49에서 39/49로 오히려 나빠졌다.

### 코드 변경
- `SyntheticBoxRenderer`: `_util.Render(true, false)`로 촬영, 박스·구성품 재질 복사본(`ReflectionFreeMaterial`)으로 환경 반사 끔, 조명 값을 `SyntheticLighting`으로 분리, 누운 원기둥 배치, 판·상자는 서 있을 때 각도 사용.
- `SyntheticVariation`, `RandomizationRanges`, `SyntheticRandomizationSO`, `Config/SyntheticRandomization.asset`: 눕는 확률과 각도(`ItemLyingChance`, `ItemLyingYawDegrees`)를 추가. 새 난수는 맨 끝에서 뽑아 같은 시드의 기존 값이 바뀌지 않게 했다. 조명 방향 범위는 25°/10°로 좁힘.
- `InspectionBackground`(런타임)를 검사 카메라와 합성이 함께 쓴다.
- 데이터셋 생성을 창에서 분리했다(`SyntheticDatasetGenerator`, `SyntheticDatasetBatch`). 배치로 만들 수 있다.
- 시험: `SyntheticVariationTests`에 눕는 확률, 눕는 각도, 다른 값이 안 바뀜을 추가(13개 통과).

### 아직 확인하지 못한 것, 한계
- **에디터 화면에서 "2개 성공, 1개 불량"이 나오는지**는 확인하지 못했다.
- 이 모델은 **씬의 조명(방향·색·세기), 박스 재질, SSAO 설정, 검사 카메라 높이에 맞춘 것**이다. 이 중 하나를 바꾸면 위의 위치별 밝기 비교부터 다시 하고, 어긋나면 데이터를 다시 만들어 재학습한다.
- 누운 확률 0.85는 키트 6장, 원기둥 11개에서 센 값이다. 표본이 작고 키팅 방식이 바뀌면 달라진다.
- 판·상자가 기울거나 비스듬히 놓인 자세(예: 비스듬히 누운 장갑)는 학습 데이터에 없다.
- SSAO가 어두운 면의 이유라는 것은 추정이다(위 3-3).
- 합성 이미지에는 SSAO가 없어서, 박스 모서리와 바닥 이음부의 어두운 정도는 씬과 정확히 같지 않다. 크롭 정확도가 이것에 흔들리지 않는지는 새 조건에서 샘플로 재야 한다.

### 다시 재는 방법
1. 데이터셋: `Unity.exe -batchmode -projectPath <경로> -executeMethod SyntheticDatasetBatch.Generate -datasetSeed <시드>` (촬영에 그리기 장치가 필요하므로 `-nographics` 없이).

### 배운 점
- **합성 점수와 씬 점수는 따로 본다.** 합성 테스트는 같은 분포 안의 점수라 씬의 오류를 못 잡는다. 정답을 아는 씬 이미지(실제 크롭, 샘플 박스)로 채점해야 한다.
- **원인은 추측하지 말고 측정한다.** 가림 실험은 모델이 어디를 보는지, 광원 하나씩 렌더는 밝기가 어디서 오는지 바로 보여 줬다. 반대로 방향·그림자·환경광 가설은 측정 없이 세웠다가 시간을 썼다.
- **미리보기 렌더러는 씬 렌더가 아니다.** 렌더러 기능(SSAO), 환경광 적용 시점, 환경 반사가 다르다. 같은 박스를 양쪽에서 찍어 위치별 밝기를 비교하는 것이 가장 빠른 점검이다.
- **값 하나를 다른 용도로 덮어쓰지 않는다.** 눕는 각도가 서 있는 각도를 덮어써서 상관없는 구성품이 틀어졌다. 용도별로 값을 따로 둔다.
- **한 번에 하나만 바꾼다.** 3-1과 3-2는 같이 고쳐서 각각의 효과를 알 수 없다.
- 새 오류가 생기면(43/49 → 39/49) 고친 것이 틀렸다는 뜻이 아니라 가려져 있던 다음 원인이 드러난 것일 수 있다. 오답을 모아서 본다.
