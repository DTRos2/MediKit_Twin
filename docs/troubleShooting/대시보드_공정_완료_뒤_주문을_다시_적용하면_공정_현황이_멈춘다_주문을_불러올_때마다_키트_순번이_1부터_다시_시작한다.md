# 대시보드: 공정 완료 뒤 주문을 다시 "적용"하면 공정 현황이 "공정 완료"에서 멈춘다 (주문을 불러올 때마다 키트 순번이 1부터 다시 시작한다)

> 작성일: 2026-11-04 · 브랜치: `feature/pw-order-dashboard-hierarchy` · Unity 6000.6.0f1
> 범위: 주문 패널에서 "적용"을 눌러 작업이 끝나 공정 현황에 "공정 완료"가 뜬 뒤, 다시 "적용"을 눌렀을 때 공정 현황 패널이 새 주문을 처음부터 따라가야 한다는 요청
> 표시: **확정**(측정이나 코드로 확인) · **추정**(코드나 정황으로 본 것) · **미검증**(아직 확인하지 않음)

## 0. 한 줄 요약

주문을 다시 불러오면 키트 순번이 1부터 다시 시작하는데, 공정 현황 집계(`ProcessTally`)가 키트를 **순번으로** 구분하고 "지금 키트보다 앞선 순번의 신호는 무시"해서 새 주문의 키트가 이미 센 키트로 취급됐다 (코드 경로로 확인). 키트를 **객체로** 구분하고, 앞선 키트 판단을 **키팅 시작 시각**으로 바꾸고, 새 주문이 적용되면 **지금 키트와 단계만** 처음 상태로 돌렸다. 센 값(완료·불량·재고 부족·오류)은 **초기화하지 않고 누적**한다. 헤드리스에서 키트 1개짜리 주문을 두 번 적용하는 전체 공정 시험이 통과했다. 에디터에서 직접 눌러 본 확인은 아직 없다 (미검증).

## 1. 요청과 방향이 바뀐 곳

- 요청: "공정 현황에서 적용을 눌러 작업이 다 끝나면 공정 완료가 뜨고, 다시 적용을 누르면 초기화되고 처음부터 적용되게 해 줘."
- 처음 계획은 집계를 0부터 다시 세는 것이었다. 사용자가 **"공정 현황 집계는 초기화가 아니라 누적되게 해줘"**라고 바로잡아서, 집계는 지우지 않고 이어서 세고 화면의 "지금 키트"와 단계만 처음 상태로 돌리는 쪽으로 바꿨다.

## 2. 원인 (확정: 코드 경로, 미검증: 수정 전 코드로 화면 재현)

1. `OrderManager.TryGetNext`가 키트를 내줄 때 `++_lastKitSequence`로 순번을 매긴다. `OrderSession.Load`는 주문을 불러올 때마다 **새 `OrderManager`**를 만들므로 순번이 1부터 다시 시작한다. 이것은 일부러 그렇게 한 것이다: 같은 주문 파일이면 같은 키트에서 누락이 나야 해서(NFR-06) 누락 규칙이 순번을 쓴다. 그래서 순번은 바꾸지 않는다.
2. `ProcessTally`는 완료·불량을 `HashSet<int>`(순번)로 세어서, 첫 주문의 1번 키트를 센 뒤 둘째 주문의 1번 키트가 와도 "이미 센 키트"라 완료 수가 오르지 않는다.
3. `ProcessTally.Follow`는 `kit.KitSequence < CurrentKit.KitSequence`이면 신호를 무시한다. 첫 주문의 마지막 키트(예: 3번)가 지금 키트로 남아 있으면 둘째 주문의 1·2번 키트 신호는 화면을 못 움직인다.
4. 그래서 화면이 첫 주문의 "공정 완료"에 머문다.
- `KitData.KitSequence`의 주석이 "실행 안에서 유일하다"고 되어 있었는데 실제로는 틀렸다. 고쳤다.

## 3. 고침 (확정)

| 바꾼 곳 | 내용 |
|---|---|
| `ProcessTally` | 완료·불량 집합을 순번(`int`)에서 키트 객체(`KitData`)로 바꿨다. `Follow`의 "앞선 키트" 판단을 `KitDispatchOrder.IsEarlier`로 바꿨다. `OnOrdersApplied()`를 더했다: 지금 키트와 단계만 처음 상태로 돌리고, 센 값·설비 상태·마지막 경고는 그대로 둔다. 화면이 안 바뀌었으면 `Version`을 올리지 않는다. |
| `KitDispatchOrder` (새) | 둘 다 `StartTime`이 있으면 시작 시각으로, 아니면 순번으로 먼저 투입된 쪽을 가른다. 시작 시각은 어느 주문의 키트든 투입 순서대로 늘어난다. |
| `OrderAppliedDetector` (새) | `IOrderInput.LastIntake`가 지난번과 다른 객체가 되면 "새로 적용됐다"고 알린다. 처음 본 값은 기준으로만 삼는다. |
| `ProcessStatusPanelPresenter` | 주문 입력(`IOrderInput`)을 씬에서 늦게 찾아 두고(`LazyComponentFinder`) 매 프레임 `OrderAppliedDetector`로 살핀다. 바뀌면 `ProcessTally.OnOrdersApplied()`를 부른다. |
| `KitData` | 순번 주석을 바로잡았다. |

- **고르지 않은 길**
  - 집계를 0으로 초기화: 사용자가 누적을 원했다.
  - `CellEvents`에 "주문 적용됨" 신호 추가: 팀 공용 계약(`INTERFACES.md`)을 바꾸게 된다. 주문 패널이 이미 `LastIntake`가 바뀌는 것을 보는 방식과 같게 해서 피했다.
  - 키트 구분에 `LotNumber` 사용: 실행 안에서 유일하지만 먼저 투입된 쪽을 문자열로 가르기는 취약하다.
  - "처음 본 순서"로 앞선 키트 판단: 패널이 켜지기 전 키트의 늦은 신호가 새 키트로 보여 기존 시험(`ALateSignalOfAnEarlierKit…`)이 깨진다.
- 주문 패널의 화면 갱신은 건드리지 않았다.

## 4. 확인 (모두 헤드리스)

- 처음 돌린 `ReapplyOrderProcessTests`는 하역 대수 단언(기대 2, 실제 1)에서 실패했다. 제품 문제가 아니라 시험이 "공정 완료"가 뜨자마자 끝나서 하역 대역(끝에 닿고 2초 뒤에 박스를 치움)에 시간을 주지 않은 것이었다. 하역 시간만큼 더 돌린 뒤 확인하도록 고쳤다.

## 5. 아직 남은 것 (미검증)

- 새 시험을 **수정 전 코드로 돌려 실제로 실패하는지**는 확인하지 않았다(논리상 실패해야 한다).
- 주문을 적용하는 순간 만들던 키트가 있는 경우(`OrderSession`은 만들던 키트를 끝까지 만든다)는 EditMode 시험(`ALateSignalOfTheOldOrdersKit…`, `AKitOfANewOrder…`)으로만 확인했고 전체 공정으로는 돌리지 않았다.
- 둘째 주문부터는 선반 재고가 줄어든 상태에서 시작한다. 재고 보충이나 초기화는 이번 요청이 아니라 건드리지 않았다.
- 에디터에서 "적용"을 두 번 눌러 보는 확인.
