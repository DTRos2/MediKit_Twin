## 1. E2E 시험 돌리는 법

`Assets/_Project/Tests/PlayMode/KittingEndToEndTests`가 `Scene_Cell`을 열고, 화면의 "적용"과 같은 방법(`IOrderInput.LoadText`)으로 주문을 넣어 집기·옮기기·놓기·다음 키트까지 돌린다.

```
Unity.exe -batchmode -projectPath <프로젝트> -runTests -testPlatform PlayMode ^
  -testFilter "MediKitTwin.PlayMode.Tests.KittingEndToEndTests.<시험이름>" ^
  -testResults <결과.xml> -logFile <로그.log>
```

| 시험 | 내용 | 시뮬레이션 시간 |
|---|---|---|
| `OneKit_IsPickedFromTheShelf_CarriedAndPlacedInTheBox` | A행(EM) 1키트 | 약 60초 |
| `BlKit_IsMadeFromTheBRow` | B행(BL) 1키트 | 약 80초 |
| `DxKit_IsMadeFromTheCRow` | C행(DX) 1키트 | 약 100초 |
| `TwoKits_AreMadeOneAfterAnother` | EM 2키트 | |
| `DefaultOrder_AllKitsAreMadeOneAfterAnother` | 기본 주문 7키트 | 약 570초 (실제 약 300초) |
| `RandomOrder_EveryKitIsMadeAndPlacedCleanly` | 랜덤 주문 (3절) | 키트당 약 70초 (시드 1, 2 기준) |
| `RandomRecipeAndOrder_EveryKitIsMadeAndPlacedCleanly` | 랜덤 주문 + 키트 구성품까지 랜덤 (3절) | 키트당 약 70초 |

- EditMode 단위 시험: `-testPlatform EditMode -nographics -assemblyNames "MediKitTwin.ArmA.Tests"`.
- E2E에는 `-nographics`를 쓰지 않는다. 도구 카메라가 RenderTexture를 쓴다.
- 결과는 로그의 `[E2E]` 줄과 결과 XML의 실패 메시지에 있다.

## 2. 실패했을 때 로그에 붙는 기록

`KittingRun`이 끝나면 `[E2E]` 보고를 낸다. 키트를 다 끝내지 못하면 더 많이 붙는다.

| 로그 줄 | 만드는 쪽 | 읽는 법 |
|---|---|---|
| `[E2E] 결과` / `마지막 결과` | `KittingRun` | 끝난 이유(키트 완료, 오류로 중단, 시간 초과)와 키팅 설비의 마지막 메시지 |
| `[E2E] 진행 기록` | `KittingProgressRecorder` | 키트와 슬롯의 단계(`Waiting` / `Picking` / `Placing` / `Placed`)가 바뀐 시각. 마지막 슬롯은 `Placed` 없이 키트가 끝난다 |
| `[E2E] 단계별 팔 베이스 위치와 파고든 곳` | `StageBaseLog` + `ArmOverlapProbe` | 단계가 바뀔 때의 팔 베이스 위치, 첫 관절 각도, 팔이 장애물과 겹친 곳과 깊이 |
| `[E2E] 첫째 관절 움직임과 팔 베이스 위치` | `JointTraceRecorder` | 첫 관절이 1° 넘게 움직이거나 베이스가 1cm 넘게 움직일 때만 기록 (5초마다 한 줄은 남김, 1500줄까지) |
| 홈 자세와의 간격 | `ArmHomeGapDump` | 실패 순간 어느 관절이 홈에서 얼마나 벗어났는지. 접기 허용 오차를 `ArmBaseApproachConfigSO`에서 읽는다 |
| 도구 끝점 경로 | `ToolPathRecorder` | 0.25초 간격의 도구 끝점 |
| `[E2E] 박스에 놓인 물건` | `PlacedItemSnapshot` | 박스 자식이 된 물건 수와 박스 안 여부 |
| `[E2E] 놓기:` | `AssertPlacedCleanly` | 멈추지 못한 물건 수, 선반보다 가장 많이 기운 각도 |

로봇 쪽 로그(`fr5_robot:`)에서 자주 보는 줄:

| 로그 | 뜻 |
|---|---|
| `박스 슬롯 위로 팔 뻗기: 서는 자리(뒤로 …m)에서 팔이 닿는 방향을 60가지(닿지 않음 N가지, 닿지만 장애물과 겹침 N가지. 가장 자주 겹친 곳: …)` | 방향 찾기가 실패한 이유 집계 |
| `…도구 방향을 기본에서 기울이기 …°, 좌우 …°로 바꾼다(N번째 후보)` | 방향 찾기가 고른 후보 |
| `박스: 슬롯 중심보다 Ncm 위에서 놓는다(닿는 가장 낮은 높이)` | 놓는 높이 사다리의 결과 |
| `박스: 서는 자리에서 팔 베이스가 … 겹쳐 Ncm 물러나 선다` | 베이스-레일 겹침 피하기 |
| `놓은 물건 …이(가) N초 만에 멈췄다. 슬롯 자리에서 가로로 Ncm 벗어났고, 선반에 놓여 있던 때보다 N° 기울었다` | 착지 결과 |
| `놓은 물건 …이(가) 놓자마자 튀었다 …` | 튕김과 놓은 직후의 겹침 기록 (`LandingTrace`) |
| `박스 진단: …` | 3절의 `BoxPlaceDiagnostics`. 쥔 물건 거리, 가늠한 자리와 실행할 자리의 차이와 IK 결과, 놓기 직전 미끄러짐 |

## 3. 랜덤 주문 시험

### 왜 만들었나

정해 둔 주문(기본 주문)은 키트 순서가 늘 같아서, 키트 종류를 번갈아 만들거나 같은 종류를 반복했을 때만 생기는 문제를 놓친다. 예를 들어 기본 순서에서만 슬롯 위 IK 실패가 한 번 나왔다. 입력을 흔들어 실패하는 조합을 찾는 시험이고, 강화학습처럼 배우는 것이 아니다. 로봇의 문제는 선반 칸 12가지 안팎에서 박스 슬롯 4개로 가는 정해진 일이라 학습이 필요하지 않다.

### 구성

| 파일 | 하는 일 |
|---|---|
| `RandomOrderGenerator` | 시드로 `순번,병원,키트코드,수량` CSV를 만든다. 같은 시드면 같은 주문이다. 키트 코드는 주입받는다 |
| `GeneratedOrder` | 시드, CSV, 키트 총수, 요약(`EM×1, DX×2 …`)을 담는다 |
| `RandomOrderSettings` | 환경 변수에서 시드와 키트 수를 읽는다. 잘못된 값이면 기본값 |
| `KittingEndToEndTests.RandomOrder_…` | 씬의 `RecipeSO`에서 키트 코드를 읽어 주문을 만들고 돌린다 |

### 쓰는 법

```
MEDIKIT_E2E_SEED=7  MEDIKIT_E2E_KITS=5
Unity.exe -batchmode -projectPath <프로젝트> -runTests -testPlatform PlayMode ^
  -testFilter "MediKitTwin.PlayMode.Tests.KittingEndToEndTests.RandomOrder_EveryKitIsMadeAndPlacedCleanly" ^
  -testResults <결과.xml> -logFile <로그.log>
```

| 환경 변수 | 기본값 | 범위 |
|---|---|---|
| `MEDIKIT_E2E_SEED` | 1 | 아무 정수 |
| `MEDIKIT_E2E_KITS` | 5 | 1 ~ 20 |

- 주문 한 줄의 수량은 최대 2다. 작을수록 키트 종류가 자주 바뀐다.
- 제한 시간은 키트 수에 맞춰 늘어난다 (시뮬레이션 120초 + 키트당 150초, 실제 120초 + 키트당 100초).
- 로그 첫머리에 `[E2E] 랜덤 주문(시드 N, 키트 K개): …`와 CSV가 나온다. 실패 메시지도 같은 설명으로 시작하므로 **같은 시드를 다시 주면 같은 주문으로 다시 돌려 볼 수 있다.**
- 단위 시험: `-testPlatform PlayMode -testFilter "MediKitTwin.PlayMode.Tests.RandomOrderGeneratorTests;MediKitTwin.PlayMode.Tests.RandomOrderSettingsTests"` (17개).
- 이 시험은 지금 알려진 문제(놓는 순간 미끄러짐, 슬롯 위 IK)를 만나면 **실패하는 것이 정상**이다. 새로운 실패 조합을 찾는 데 쓴다.
- 시드 1~10의 실행 결과는 [시드 모음 문서](FR-03_랜덤_주문_시험_시드_1_10_실패_종류_모음.md)에 있다.

### 구성품까지 섞는 시험 (`RandomRecipeAndOrder_…`)

주문은 "무슨 키트를 몇 개"를 흔들 뿐 키트 안의 구성은 레시피 에셋(EM, BL, DX)으로 늘 같다. 이 시험은 같은 시드로 **레시피의 구성품 구성도** 바꾼다. 레시피가 바뀌어도(다른 칸에서, 다른 순서로 집어, 다른 슬롯에 놓아도) 팔이 키트를 만드는지 본다. 예를 들어 CSV 주문이 아니라 키트 구성이 달라지는 경우다.

| 정하는 것 | 범위 |
|---|---|
| 구성품 수 | 3 ~ 4개 (`RandomMinItemsPerKit`, `RandomMaxItemsPerKit`). 한 개짜리는 시험하는 것이 적다 |
| 구성품 | 선반 12칸의 (칸, 구성품) 짝 중에서. 행이 달라도 된다 (EM 키트가 B행·C행 칸을 집을 수 있다) |
| 집는 순서 | 섞는다 |
| 놓을 슬롯 | 슬롯 번호 1~n을 구성품에 섞어 배정한다. 슬롯 번호 k는 좌표 목록의 k번째와 짝이다 (구성품이 4개보다 적으면 앞의 슬롯만 쓴다) |
| 그대로 두는 것 | 키트 코드, 상자 크기. 주문 검사가 어긋나지 않게 한다 |

- 칸 안의 물건은 씬에 이미 놓여 있어서 새 구성품을 만들 수는 없고, 있는 12칸 안에서만 고른다.
- 같은 시드를 `MEDIKIT_E2E_SEED`로 주면 주문과 구성이 함께 재현된다. 구성은 주문과 난수열이 겹치지 않게 시드를 한 번 비튼다.
- 로그 첫머리에 `[E2E] 바꾼 구성`이 키트마다 한 줄씩 나온다 (예: `EM: 1.C-1 swab→슬롯3, 2.B-3 alcohol_pad→슬롯4, ...`). 번호는 집는 순서다. 실패 메시지에도 같이 붙는다.
- **에셋 파일은 바뀌지 않는다.** `JsonUtility.FromJsonOverwrite`로 메모리의 객체만 덮어쓰고, 시험이 끝나면(실패해도 `finally`에서) 원래대로 되돌린다. 제품 코드에 값을 바꾸는 메서드를 열지 않았다. 시험 뒤 `git status`에 `Recipes/*.asset`이 나오지 않아야 한다.
- 한 칸의 시작 재고가 5개(`ScenarioConfig_Default`)라 키트를 5개보다 많이 만들면 칸이 바닥나 보충(30초)을 기다린다. 그 동작을 보려는 시험이 아니면 키트 수를 5 이하로 둔다.
- 구성: `RecipeContentRandomizer`(적용·복원), `RandomRecipeGenerator`(구성 정하기, 씬 없이 시험 가능), `RandomRecipe`, `RandomRecipeItem`, `ShelfCellContent`, `RandomShuffle`, 덮어쓰기용 사본 `RecipeData`·`RecipeItemData`.
- 단위 시험: `RandomRecipeGeneratorTests`, `RecipeContentRandomizerTests` (28개). `RecipeItemData`의 필드 이름이 `RecipeItem`과 어긋나면 `RecipeContentRandomizerTests`가 먼저 알려 준다.

## 4. 운용 함정

| 함정 | 증상·이유 | 대처 |
|---|---|---|
| 에디터가 열려 있음 | 프로젝트 잠금으로 배치가 못 돈다 | Unity 에디터를 닫는다 |
| 한 프로세스에서 시험 둘 | 씬을 다시 불러오면 GPU Resident Drawer 작업 스레드에서 Unity가 죽는다 (`ParallelFilterChangedInstancesAndCreateScriptingArray`) | **시험 하나마다 Unity를 따로 띄운다** |
| 팔 링크에 접촉 알림 | `OnCollision*`을 ArticulationBody 링크에 달면 PhysX 물리 단계(`PxsSolverStartTask::setupDescTask`)에서 죽는다 | 겹침은 `Physics.OverlapBox` / `ComputePenetration` 조회로 본다 |
| 크래시한 실행 | `Assets/InitTestScene<guid>.unity`(+meta)를 남긴다 | 지운다. `Assets/_Recovery`는 건드리지 않는다 |
| 배치가 도는 동안 소스를 고침 | 중간에 다시 컴파일되어 결과가 섞일 수 있다 | 끝난 뒤에 고친다. `Assets` 밖 문서는 괜찮다 |
| 씬 값을 실험함 | 배치는 씬 파일을 바꾸지 않지만 실험하다 바뀔 수 있다 | 백업하고 `cmp`로 복구를 확인한다 |
| 같은 로그를 덮어씀 | 시험 이름이 파일 이름이라 다시 돌리면 이전 결과가 사라진다 | 실행마다 출력 폴더를 바꾼다 |

## 5. 처음 잘못 읽은 것 (다시 틀리지 않으려고 남긴다)

| 처음 읽은 것 | 실제 |
|---|---|
| 관절 덤프의 "목표"가 팔이 가려던 목표다 | 구동 명령이다. `JointCommandLead`가 명령을 현재 각도 ± `_maxCommandLeadDeg`(5°)로 잘라 보내므로 실제 목표가 아니다 |
| IK 오차가 1.9mm면 아슬아슬하게 닿는다 | IK는 오차가 2mm 아래로 처음 내려오면 멈춘다. 수렴한 결과는 늘 1.5 ~ 1.9mm 근처에 몰린다. 실패는 오차 크기가 아니라 `수렴 못함` 표시다 |
| 두 번째 키트에서 집기 거리가 26cm → 32cm로 늘었으니 앞 키트가 베이스를 6cm 어긋나게 남겼다 | A행 칸 4곳 모두 같은 만큼 늘었다. 베이스가 어긋난 것이 아니라 물건 위치가 다르다 (같은 칸의 두 번째 물건이 안쪽에 있다는 **추정**) |
| 같은 입력이면 같은 결과가 나온다 | 방향 찾기가 한 프레임에 쓰는 시간을 실제 시간으로 재서(`CreateSearchBudget`) 컴퓨터 속도에 따라 프레임 수가 달라진다. 실행마다 결과가 조금 다를 수 있다 |
| 베이스가 레일에 파고들면 무조건 실패한다 | 얕게(0.9cm) 파고드는 A행은 통과했다. 깊이에 따라 갈린다 |

### 새로 찾은 실패: 세 번째 BL 키트의 B-2에서 집지 못함 (시드 3)

```
선반 칸 B-2에서 집지 못했다. 그리퍼를 닫았지만 물건을 쥐지 못했다: 손가락이 물건에 닿지 않고 끝까지 닫혔다(물건이 손가락 사이에 있지 않다) — 물건 중심이 도구 끝점에서 0.016m 떨어져 있다(쥐는 반경 0.060m)
```

| 확인한 것 | 값 |
|---|---|
| 같은 칸 B-2 (바늘)의 앞 두 번 | 키트 1, 2에서는 같은 로그 조건으로 쥐었다 |
| 카메라 보정 | 세 번 모두 높이 +8.0cm로 보정 (한계 8.0cm에 걸림), 쥐는 자리 높이 0.951m, 물건 중심 0.923 ~ 0.925m |
| 알려 준 자리와 물건의 수평 거리 | 24.5cm → 29.8cm → **43.9cm** (B-1은 24.4 → 31.8 → 46.7cm) |
| 알려 준 관절 값과의 차이 | j4 8.1° → 9.0° → 9.4°, j2 7.6° → 5.6° → 5.6° (세 번 비슷함) |
| 실패 뒤 | 다시 시도하지 않고 바로 `Fault`로 끝남 |

- 쥐는 자리 높이와 관절 차이는 성공한 앞 두 번과 거의 같아서, 그 값으로는 갈린 이유를 설명하지 못한다.
- **확정**: 이 한 번에서 물건 중심은 도구 끝점 1.6cm 안에 있었는데 손가락이 물건에 닿지 않고 닫혔다.
- **미검증**: 왜 닿지 않았는지. 후보는 (a) 세 번째 바늘이 선반 안쪽에서 앞의 동작에 밀려 옆으로 눕거나 기운 상태, (b) 보정이 한계 8.0cm에 걸려 실제로는 더 높게 겨냥한 상태, (c) 얇은 물건이라 손가락 사이를 지나쳐 닫힘. 어느 것인지 가를 로그가 아직 없다.
- 이전 기본 순서에서는 같은 칸이 세 번 쓰인 적이 있어도(DX) 이 실패가 없었다. 키트 코드가 반복되는 주문에서만 나오는지는 시드를 더 돌려 봐야 안다.
- 다음 측정: 닫기 직전의 물건 자세(회전)와 손가락 위치를 같은 줄에 남긴다. 같은 시드 3으로 재현되는지 먼저 본다.

## 7. 구성품까지 섞은 시험 첫 결과 (시드 1 ~ 3, 키트 5개씩)

2026-11-02에 `RandomRecipeAndOrder_…`를 시드 1, 2, 3으로 한 번씩 돌렸다. 주문은 같은 시드의 `RandomOrder_…`와 같다. 키트 안의 구성품 구성이 시드마다 달라졌다. 키트 코드(EM, BL, DX)마다 한 번씩 다시 정해지고, 그 시험 안에서는 모든 BL 키트가 같은 구성을 쓴다.

| 1 | BL, EM, DX, DX, BL | BL: C-4→1, C-3→2, C-2→3 / DX: B-4→1, A-4→3, B-2→2 / EM: C-1→3, B-3→4, A-1→2, C-2→1 | **1/5에서 중단** (111.6초). EM #2 1번 슬롯에서 슬롯 위 IK 수렴 못함 |

- 세 시드 모두 구성이 실제로 바뀐 채 돌았다. 행이 다른 칸(EM이 C행 칸을 집기 등)과 집는 순서와 슬롯 번호가 어긋난 구성(1번째로 집은 것을 3번 슬롯에 놓기 등)에서도 시드 3은 모든 키트를 만들었다.

- **구성을 바꿔서 새로 생긴 실패 종류는 없었다.** 세 시드뿐이라 구성 때문에 늘거나 줄었다고 말할 수는 없다. 이번에 나온 실패는 모두 이미 알려진 종류다 (튕김, 슬롯 위 IK).

- 구성이 바뀐 시험에서 실패했을 때는 `[E2E] 바꾼 구성` 줄과 실패 메시지의 같은 줄을 함께 본다.
