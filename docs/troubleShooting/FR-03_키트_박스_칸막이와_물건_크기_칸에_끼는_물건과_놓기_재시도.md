# FR-03 키트 박스 칸막이: 물건이 칸에 안 들어가고, 줄이면 4번 슬롯 내리기가 실패하고, 얇은 판이 칸에 낀다

> 작성일: 2026-11-03 · 브랜치: `feature/pw-conveyor-dashboard-polish`
> 범위: 키트 박스 슬롯 사이에 칸막이를 세우고(요청: "각 슬롯마다 들어갈 수 있게"), 그 과정에서 만난 문제 셋과 뚜껑 안착 간헐 실패
> 결과: 칸막이 3개 + 물건 축소 + 놓기 재시도로 A·B·C행과 뚜껑 포함 박스 이송이 **헤드리스에서** 통과했다. **에디터에서 직접 확인한 것은 없다.**
> 표시: **확정**(측정·시험으로 확인) · **추정**(정황) · **미검증**

## 0. 현재 상태 한눈에 보기

| 항목 | 상태 | 비고 |
|---|---|---|

## 1. 한 일

| 부분 | 내용 |
|---|---|
| 계산 | `Inventory/KitBoxPartitionLayout` (순수 클래스, EditMode 시험): 슬롯 좌표 → 칸막이 자리, 칸 길이, 물건 대각선 상한 |
| 설정 | `Config/KitBoxPartitionConfig.asset`: 두께, 높이, 물건과의 틈. 슬롯 좌표는 레시피(`RecipeSO`)에서 읽는다 |
| 크기 상한 | `GraspSizeLimit.WithFaceDiagonalCeiling` + `ShelfLayoutConfigSO.CreateItemSizeLimit()`: 선반 빌더, 합성 데이터 생성기, 검사 표본 생성기, 편집 도구가 같은 한도를 쓴다 |
| 편집 도구 | `Tools > MediKit > Add Kit Box Partitions` (`KitBoxPartitionSetup.Apply`): 설정 에셋 만들기 → `PF_KittingJig`의 `KitBox`에 `Divider_N` 붙이기 → `PF_Shelf` 물건 줄이기. 몇 번을 눌러도 결과가 같다 |
| 놓기 재시도 | `BoxPlaceRoutine`: 슬롯까지 내려가지 못하면 더 높은 놓는 높이부터 다시 찾는다 (`PlacementChoice` 새 파일) |

- 칸막이는 벽보다 낮아야 한다. 뚜껑 덮기가 박스 윗면을 자식 렌더러의 최고점으로 재므로(`LidCoverTask.TopOf`) 칸막이가 벽보다 높으면 뚜껑을 너무 높게 얹는다. 도구가 벽 높이로 맞춘다.

## 2. 문제 1: 칸막이를 두면 물건이 칸에 안 들어간다 (확정)

| 값 | 크기 |
|---|---|
| 슬롯 간격 | 5.47cm |
| 칸막이를 뺀 칸 길이 | 약 5.16cm |
| 물건 크기 상한(그리퍼 기준) | 6.16cm (= 열린 폭 0.077m × 0.8) |
| 박스 안쪽 폭(x) | 7.76cm |

- 물건 한 변이 최대 6.16cm라 칸막이 사이(5.16cm)에 그대로는 들어가지 않는다.
- 선택지와 결정:
  - 물건을 칸에 맞게 줄임 → **채택** (사용자 결정).
  - 박스를 길게 늘림 → 원래 크기를 지키려면 박스 길이를 약 29cm로 늘려야 한다고 어림했다(**미검증** 어림값, 시뮬레이션으로 확인하지 않음). 레시피 슬롯 좌표, 뚜껑, 컨베이어, 검사 CNN 슬롯 크롭이 함께 바뀌므로 **팀 합의가 필요**해서 미뤘다.
  - 낮은 턱만 세움 → 물건을 가두지 못해 제외.

## 3. 문제 2: 물건을 줄이자 C행 4번 슬롯 내리기가 실패한다 (확정, 헤드리스)

증상: `슬롯 4에 놓지 못했다. 박스 슬롯으로 내리기: 팔이 시간 안에 목표 자세에 닿지 못했다 — 도구 끝점 남은 오차 0.038m/4.4도`. 관절은 목표에서 2° 이내인데 끝점이 3.8cm 모자랐다.

원인을 가른 실험 (C행, 같은 시험):

| 상태 | 결과 |
|---|---|
| 칸막이 40mm + 물건 축소 | 실패 4/4 (오차 값이 거의 같음) |
| 칸막이 20mm + 물건 축소 | 실패 2/2 |
| 칸막이 없음 + 물건 축소 | 실패 1/1 |
| 칸막이 없음 + 원래 크기 | **통과** |

- 칸막이가 아니라 **물건 크기가 바뀐 것**이 방아쇠였다.
- 4번 슬롯의 놓는 방향 후보가 달라졌다. 원래 크기에서는 6번째 후보(서는 자리 0.10m 옮김, 기울이기 15°, 손목 비틀기 0°)를 골라 성공했고, 줄인 물건에서는 2번째 후보(서는 자리 0.10m 옮김, 기울이기 0°, 손목 비틀기 90°, 놓는 높이 4cm)를 골라 내려가다 멈췄다. 재시도가 7cm 높이에서 다시 찾으면 통과한다.
- 원인(추정): 방향 찾기의 "닿는다"는 슬롯 자세 하나만 IK로 풀어 보는 판정(`tool.Probe(pose).Converged`)이고, 실제 실행은 위에서 곧게 내려가는 길(`MoveToolPrecisely`)이다. 판정은 통과해도 내려가다 풀이가 따라오지 못하는 후보가 섞인다. 물건 크기가 바뀌면 어떤 후보가 먼저 뽑힐지가 바뀐다.
- 고침: `BoxPlaceRoutine`이 `BoxAbove`/`BoxSlot`에서 실패하면, 더 높은 놓는 높이가 남아 있는 한 그 위 높이부터 다시 찾는다. 첫 시도가 성공하는 경우의 동작은 같고, 원래 Fault로 끝나던 경로에서만 달라진다. 로그에 `박스: 슬롯 중심보다 4cm 위 높이로는 내려가지 못해 7cm 높이부터 다시 찾는다.`가 남는다.
- **근본 원인(사전 판정이 실행을 못 따라옴)은 그대로다.** 지금은 C행 4번 슬롯에서 이 재시도가 매번 쓰인다 (C행 3회 모두).

## 4. 문제 3: 얇은 판이 칸 안에서 끼어 안 멈춘다 (확정 + 추정, 헤드리스)

- 긴 변만 4.76cm로 줄였을 때 C행이 2회 중 1회 실패했다. 키트는 완료됐지만 4번 칸의 `sample_bag`이 2.5초 안에 멈추지 않았다(0.067m 움직임). 멈춘 자리는 슬롯 중심이 맞는데 바닥판에서 2.2cm 떠 있었다. (확정)
- 원인(추정): 칸 안에서 판이 서거나 기울면 가장 긴 변이 아니라 **큰 두 변의 대각선**만큼 칸을 차지한다. `sample_bag`은 긴 두 변이 약 4.76 × 3.33cm라 대각선이 5.8cm이고, 칸 길이(칸막이를 뺀 5.16cm)보다 커서 칸막이 사이에 비스듬히 낀 것으로 본다.
- 고침: 상한을 "큰 두 변의 대각선 ≤ 4.76cm"로 바꿨다. `sample_bag`은 6.16 × 0.92 × 4.31cm에서 약 3.9 × 0.58 × 2.7cm가 된다(계산값). 선반 60개 중 가장 큰 대각선은 6.73cm에서 4.76cm로 줄었다(편집 도구 로그).
- 결과: C행 3회 모두 통과, 멈추지 못한 물건 0개. 표본이 3회라 끼임이 완전히 없어졌다고 단정하지 않는다.

## 5. 뚜껑 안착 간헐 실패 (원인 미확정)

| 조건 | 결과 |
|---|---|
| 칸막이 없음, 원래 크기 (8회) | 6회 통과. 실패 2회: ① 덮을 높이까지 내려가지 못함(끝점 17mm 높음, 컴파일이 겹친 첫 회차) ② 안착 검사 실패(가로 4.7mm, 높이 **−9.9mm**) |
| 칸막이 + 축소 (5회) | 4회 통과(가로 1.6~4.6mm, 높이 0~6.3mm). 실패 1회: 가로 57.7mm, 높이 65.9mm (재시도 수정과 긴 변 기준 축소 상태) |

- 이전 추정("비스듬히 앉은 물건에 뚜껑이 얹힌다")은 **틀렸다.** 높이 오차가 −9.9mm(낮음)였고, 통과 회차와 실패 회차의 물건 놓이는 결과는 거의 같았다.
- 칸막이가 뚜껑 실패를 늘렸다는 증거는 없다. 칸막이 없을 때도 8회 중 2회 실패했다.
- 대각선 기준 축소 이후 3회는 모두 통과(가로 1.6 / 3.0 / 3.6mm, 높이 0.0mm).
- 실패 회차에 덮기 직전의 끝점 잔차, `TopOf` 값, 뚜껑 기울기를 로그에 남기도록 하면 원인을 가릴 수 있다. **아직 하지 않았다.**

## 7. 아직 모르는 것 / 해야 할 것

- **에디터 확인:** 칸막이 모양, 줄어든 물건(선반 60개 전부 대각선 4.76cm 이하)의 보임새, 쥐기와 카메라 인식이 에디터(가변 프레임)에서도 되는지. 에디터는 프레임이 길어 헤드리스(고정 50fps)에서 통과하던 것이 실패할 수 있다.
- **검사 CNN:** 물건 크기가 바뀌었다. 합성 데이터 생성기는 같은 상한을 쓰도록 바꿨지만 **재생성과 재학습은 하지 않았다.**
- **박스 확대:** 물건 크기를 지키려면 박스를 늘리는 쪽이 대안이다(약 29cm는 미검증 어림값). 팀(박스·슬롯·물건 크기 합의, 레시피 슬롯 좌표, 뚜껑, 컨베이어, 검사 CNN)과 정해야 한다.
- **놓기 재시도의 근본 원인:** 사전 판정과 실행의 차이(IK). 재시도는 우회이다.
- **뚜껑 안착 간헐 실패 원인.**

## 8. 되돌리는 법과 배운 것

- 되돌리기: `git checkout -- Assets/_Project/Prefabs/PF_KittingJig.prefab Assets/_Project/Prefabs/PF_Shelf.prefab` (칸막이와 물건 크기가 원래대로). 다시 적용하려면 위 메뉴를 한 번 누른다. 칸막이 높이·두께·틈은 `KitBoxPartitionConfig.asset` 값만 바꾸고 메뉴를 다시 누르면 된다.
- 원인이 둘 이상 섞인 변경(칸막이 + 물건 축소)은 **하나씩 원래대로 돌려 비교**해야 가려진다. 이번에는 "칸막이 높이 → 칸막이 유무 → 물건 크기" 순서로 되돌려 방아쇠가 물건 크기임을 찾았다.
- 한 번 실패한 시험이 매번 같은 값으로 실패하면(헤드리스는 시간이 고정) 간헐 문제가 아니라 재현되는 문제이다. 반복 시험으로 이를 먼저 가른다.
- 배치 시험이 도는 동안 `Assets` 아래 소스를 고치지 않는다(중간에 다시 컴파일된다).
