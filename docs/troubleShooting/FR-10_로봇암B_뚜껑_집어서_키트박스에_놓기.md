# FR-10 로봇암 B 뚜껑 집어서 키트 박스에 놓기 트러블슈팅

> 작성일: 2026-11-01 · 브랜치: `feature/dhj-armb-ur3`
> 범위: 로봇암 B(UR3 + Robotiq 2F-140)가 `LidSupplyTable`의 맨 위 뚜껑을 집어 올려 컨베이어 위 키트 박스(`Sensor_Packing > KitPackage > KitBox (1)`) 위에 놓기까지 구현하면서 겪은 문제
> **뚜껑을 박스에 "덮는 것"(안착 판정과 `LidClosed` 발행)은 이 문서의 범위가 아니다.** 뚜껑이 박스 위에 놓이는 데까지는 확인했지만 덮기는 실패하고 있고 원인은 아직 모른다(13절).
> 코드: `Assets/_Project/Scripts/ArmB/` (`LidCoverTask`, `LidCoverPlanner`, `LidDispenser`), `Assets/_Project/Editor/` (`CellSceneBuilder`, `ArmReachMap`, `ArmBLidSetup`)

## 0. 현재 상태 한눈에 보기

| 단계 | 상태 | 비고 |
|---|---|---|
| 뚜껑 위로 이동 | 확인함 | 마찰·댐핑을 0.1로 낮춘 뒤 |
| 뚜껑 쥘 높이까지 하강 | 확인함 | `ArmB/Base`(받침대) 콜라이더를 끄거나 줄인 상태에서 |
| 뚜껑 쥐기 | 확인함 | 물리 파지(`JointGripper`와 `Graspable`) |
| 뚜껑 들어 올리기 | 확인함 | 실제 끝점 기준으로 올리도록 고친 뒤 |
| 박스 위로 이송 | 확인함 | |

| 덮기(안착 판정, `LidClosed` 발행) | **실패, 원인 미확인** | 이 문서의 범위 밖 |

이 문서의 "해결"은 아래 표시로 구분한다.
- **확정**: 원인을 바꿔서 증상이 사라지는 것을 직접 확인함
- **추정**: 증거는 있으나 다른 가능성을 배제하지 못함
- **미검증**: 고쳤지만 Unity에서 다시 실행해 확인하지 못함

## 1. 설계 결정: `ArmB`가 `ArmA`를 참조하지 않는다

**상황**: 뚜껑을 집어 키트 박스로 옮기는 동작을 만들면서 `ToolPoseMover`(목표 자세까지 이동), `JointGripper`, `Graspable`을 쓰고 싶었는데 모두 `MediKitTwin.ArmA` 어셈블리에 있다. `ArmB` 어셈블리는 `Common`만 참조한다.

**선택지**
1. `ArmB`가 `ArmA`를 참조한다. 재사용이 쉽지만 로봇암 B가 로봇암 A 어셈블리에 묶인다.
2. `ArmB`는 `Common`의 인터페이스(`IToolPoseTarget`, `IGripper`, `IArmState`)만 쓰고, 이동 코루틴은 직접 작성한다. (선택)
3. `ToolPoseMover`를 `Common`으로 옮긴다. 팀원이 작업 중인 `ArmA` 파일을 건드리게 된다.

**결정**: 2번. `docs/INTERFACES.md`의 의존 규칙(설비끼리 직접 참조하지 않음)에 맞고, 팀원 코드에 영향이 없다. 대가로 `LidCoverTask.MoveTool`이 `ToolPoseMover`와 거의 같은 코드가 되었다(중복).
뚜껑에 붙일 `Graspable`은 `ArmA` 형식이라 런타임 코드가 아니라 에디터 도구(`ArmBLidSetup`)가 프리팹에 붙인다.

## 2. 문제: 키트 박스·뚜껑 크기를 바꿨는데 빌더 상수가 예전 값

**증상**
- `Tools > MediKit > Rebuild … Prefab`을 누르면 크기가 예전 값으로 돌아간다.
- 측정 도구가 뚜껑 반폭을 예전 값(0.235m, 0.185m)으로 고정해서 쓴다.

**원인**
- 씬과 프리팹의 크기를 손으로 고쳤지만 `CellSceneBuilder`의 상수는 그대로였다.
- 씬의 `LidSupplyTable` 인스턴스에는 뚜껑 박스 벽 높이, 뚜껑 높이(y=0.924), 승강판 같은 수작업 오버라이드가 있었고 빌더에는 없었다.

**확인한 실제 값 (씬/프리팹)**

| 항목 | 빌더 상수(이전) | 실제 값 |
|---|---|---|
| 키트 박스 | 0.44 × 0.10 × 0.34 | 0.0976 × 0.10 × 0.2387 |
| 뚜껑 바깥 | 0.47 × 0.04 × 0.37 | 0.1276 × 0.04 × 0.2687 |
| 뚜껑 박스 x·z | 0.54, 0.44 | 0.1976, 0.3387 |
| 맨 위 뚜껑 높이 (`LidPositionY`) | 0.639 | 0.924 |
| 뚜껑 박스 높이 | 0.595 | 0.88 |
| 슬롯 위치(z, 레시피 기준) | ±0.05 등 | 0.082, 0.0273, -0.0273, -0.082 |

**해결 (확정)**
- `CellSceneBuilder`의 `KitBoxSize`, 슬롯 배열, `LidPositionY`, 뚜껑 박스 높이를 실제 값으로 바꿨다. `LidBoxSize`는 `LidSize + 0.07`로 계산한다.
- `ArmReachMap`은 고정값을 지우고 뚜껑의 실제 크기에서 계산하도록 고쳤다.
- 뚜껑 박스를 다시 만드는 메뉴가 없어서 `Tools > MediKit > Rebuild LidSupplyTable Prefab`을 추가했다. 이 메뉴는 `LidDispenser`를 중복으로 붙이지 않는다.

**교훈**: 씬이나 프리팹을 손으로 고치면 빌더 상수에도 같은 값을 넣는다. 안 그러면 다음 Rebuild에서 조용히 되돌아간다.

## 3. 문제: 측정 도구가 뚜껑 크기를 잘못 읽음

**증상**: `Measure ArmB Reach`가 "뚜껑 크기 x 0.2702 · z 0.1308, 그리퍼 벌림보다 넓음"이라고 출력. 실제 뚜껑은 0.1276 × 0.2687인데 x와 z가 뒤바뀌어 나왔다.

**원인**: 렌더러의 월드 축 정렬 경계 상자(`Renderer.bounds`)로 크기를 쟀다. 뚜껑이 월드에서 약 90° 돌아 있어서(월드 yaw 269.3°, 긴 변이 월드 -X를 향함) 폭과 길이가 바뀌었다. 0.2702/0.1308이 0.2687/0.1276과 조금 어긋난 것은 90°가 아니라 약 0.7° 더 돌아 있기 때문이다.

**해결 (확정)**: 뚜껑 자신의 로컬 축 기준으로 메시 경계를 재도록 고쳤다(`TryGetLocalSize`). 이후 "x 0.1276 · y 0.0400 · z 0.2687"이 정상으로 출력되었다.

**참고**: 뚜껑은 긴 변이 월드 -X를 가리키고(측정값), 키트 박스는 Scene 뷰 위에서 본 모양으로 긴 변이 Z 방향이다. 둘 다 팔 베이스에서 보면 반경 방향이라서 베이스를 약 90° 돌리면 뚜껑 방향이 박스와 맞고, 손목을 따로 돌릴 필요가 없다.

## 4. 문제: 뚜껑 위로 이동하지 못함 — IK는 풀리는데 팔이 목표에 못 감

**증상**: `LidCoverTask`가 "뚜껑 위로 이동하지 못했습니다"로 실패. Step Timeout을 3초에서 10초로 늘려도 같은 곳에서 멈춘다.

**진단 과정**
1. 실패 메시지에 IK 오차를 넣어 확인 → IK 위치 오차 1.3mm, 회전 오차 0.0°. **목표는 풀리는 점**이다.
2. 실제 끝점과 목표의 차이를 출력하게 함 → x -5mm, y +11mm, z +24mm, 회전 4.2°. 어긋난 방식이 "베이스 회전(J1)이 약 3~4° 모자란" 것과 같았다.
3. 관절별 현재 각도, IK 목표 각도, 한계를 출력하게 함 →

| 관절 | 현재 | 목표 | 차이 |
|---|---|---|---|
| shoulder_pan | 76.7° | 80.2° | -3.5° |
| shoulder_lift | 110.6° | 112.1° | -1.5° |
| elbow 이하 4개 | 거의 일치 | | 0.1~0.5° |

관절 한계는 ±180°라서 한계 문제가 아니다. 가장 하중을 받는 두 관절(pan, lift)만 목표에 못 간다.

4. `Report ArmB Contacts`는 "겹친 충돌체 없음". 충돌이 아니라 구동 쪽 문제로 판단했다.

**원인 (확정)**: `ArmDriveSetup`(`ArmDriveSettings`)가 모든 관절에 **Joint Friction 10, Damping 10**을 준다. Unity 기본값(0.05)의 200배다. 팀원이 FR5에서 같은 증상을 겪고 고친 커밋(`9f6d163`, "FR5 관절 마찰과 댐핑 값 수정")과 같은 원인이다. 그 커밋은 UR3는 가벼워서 같은 값으로도 문제없다고 했지만, 우리 UR3는 어깨 두 관절이 목표에 못 갔다.

**해결 (확정)**: `ur3_with_gripper`의 `Arm Drive Setup`에서 `Joint Friction`과 `Damping`을 10에서 0.1로 바꿨다. 이후 뚜껑 위로 이동이 통과했다.
- 이 값은 `Scene_Cell.unity`에 들어가는 변경이다. 팀 공유 씬이므로 알려야 한다.
- 마찰과 댐핑을 같이 바꿔서 어느 쪽이 결정적이었는지는 가리지 않았다(팀원 메모와 같은 한계).

## 5. 문제: 그리퍼 패드 간격이 뚜껑 폭과 거의 같음

**증상**: 하강하면 한쪽 손가락 패드가 뚜껑 옆면이 아니라 **윗판 위에 얹히거나 옆면에 바짝 붙는다.** 접촉 보고에 `right_inner_finger_pad ↔ Lid_01/Top`, 겹침 깊이 0.1~0.2cm.

**원인 (확정)**: 뚜껑 폭을 정할 때 "그리퍼 최대 벌림 0.14m"를 기준으로 삼았는데, 0.14m는 **패드 바깥 면 사이** 값이었다. 뚜껑이 들어가는 **안쪽 간격**은 이보다 작다. `Tools > MediKit > Measure ArmB Gripper Gap`(새로 추가)로 측정:

| 항목 | 값 |
|---|---|
| 오른쪽 패드(닫히는 방향, TCP 기준) | -0.0718 ~ -0.0643 (두께 약 7.5mm) |
| 왼쪽 패드 | 0.0643 ~ 0.0718 |
| 패드 사이 간격 | **0.1285m** |
| 뚜껑 폭 | 0.1276m → 한쪽 여유 **0.5mm** |
| 패드 높이 | TCP 기준 -0.028 ~ +0.042m (TCP 아래로 4.2cm) |
| TCP 위치 | 두 패드의 정중앙 (오차 0.1mm 이내) |

한쪽 여유가 0.5mm이면 정렬 오차 3mm로도 한 패드는 항상 윗판에 걸린다.

**해결 (확정)**: 뚜껑 벽 두께(`LidWall`)를 10mm에서 5mm로 줄여 뚜껑 폭을 0.1276m에서 **0.1176m**로 했다. 키트 박스(0.0976 × 0.2387), 슬롯, 레시피는 그대로다. 뚜껑과 박스 사이 틈도 5mm 그대로다. 측정 결과 한쪽 여유 **5.5mm**.
- 대안으로 키트 박스를 좁히는 안(한쪽 약 10mm)도 검토했지만 박스 안 구성품 배치와 레시피를 다시 맞춰야 해서 선택하지 않았다.

**교훈**: 그리퍼 사양의 "최대 벌림"은 패드 안쪽 간격이 아닐 수 있다. 크기를 정하기 전에 시뮬레이션 모델에서 실제 패드 콜라이더 간격을 측정한다.

## 6. 문제: 여유 5.5mm인데도 하강하면서 한쪽이 뚜껑에 붙음

**증상**: 시작할 때는 뚜껑이 두 손가락 사이 한가운데에 오지만, 내려오는 도중 한쪽 패드가 뚜껑 -x 옆면에 붙어서 내려가다 멈춘다.

**진단 과정**
1. 하강을 한 번에 하면 관절이 관절 공간에서 직선으로 움직여 끝점이 옆으로 휜다. → 하강을 `linearStepM`(처음 2cm, 이후 1cm)씩 끊어서 이동하도록 바꿨다.
2. 판정이 "목표와의 거리 3mm" 하나라서, 쥐는 데 영향이 거의 없는 높이(y) 처짐과 긴 변 방향 오차 때문에 계속 실패했다. → 방향별 판정으로 바꿨다.
   - 쥘 때: 손가락이 닫히는 방향만 엄격(3mm→2mm), 나머지는 10mm
   - 박스 위에 놓을 때: 가로 두 방향 엄격, 높이는 10mm
3. 중력과 마찰로 끝점이 7~12mm 처지는 것을 상쇄하려고 실제 끝점 오차를 보며 목표를 옮기는 적분 보정(`correctionGain`, 최대 20mm)을 추가했다.
4. 실패 메시지에 패드-뚜껑 옆면 간격을 넣었다. 예: `닫히는 방향 -쪽 -1.3mm, +쪽 10.5mm` → 한쪽 패드가 1.3mm 파고들고 반대쪽은 10.5mm 벌어져 **패드 중심이 뚜껑 중심에서 약 5.9mm 치우침**. 한쪽 여유 5.5mm보다 크다.

**결과**: 위 개선만으로는 해결되지 않았다. 아래 7번의 원인을 찾고 나서 해소되었다. 4번의 패드-뚜껑 간격 진단은 이후에도 유용해서 남겼다.

## 7. 문제: 어깨 lift가 128~129°에서 멈춤 — 받침대(`ArmB/Base`) 충돌

**증상**: 쥘 높이로 내려가다 어깨 lift(`shoulder_lift`, `upper_arm_link`)가 목표와 상관없이 **같은 각도에서 멈추고**, 그 상태에서 끝점이 옆으로 밀린다.

| 실행 | lift 현재 | lift 목표 |
|---|---|---|
| 1 | 127.9° | 128.9° |
| 2 | 127.8° | 132.0° |
| 3 | 127.7° | 136.6° |
| 4 | 128.6° | 136.9° |
| 5 | 128.8° | 135.2° |

목표를 129°에서 137°로, 뚜껑 박스 x 위치를 바꿔도 128~129°에서 멈춘다 → 하드 스톱처럼 보인다.

**진단**
- `Report ArmB Joint Limits`(새로 추가): 물리 엔진 기준 한계가 `[-180, 180]`, 강성 10000, 힘 한계 1000. **관절 한계가 아니다.**
- `Report ArmB Contacts`는 계속 "겹침 없음". 이 도구는 겹침 깊이가 0인 단순 접촉을 "겹침 없음"으로 처리해서, 살짝 닿은 접촉은 보이지 않는다. **"접촉 없음"이 부딪힘이 없다는 증거가 아니었다.**
- `ArmB/Base`(받침대) 콜라이더를 끄고 같은 테스트를 하자 **뚜껑을 잡고 들어 올려 박스 위에 놓는 데까지 진행했다.**

**원인 (추정)**: 윗팔(또는 인접 링크)이 받침대 윗면 모서리에 걸린다. 어느 링크가 받침대의 어느 면에 닿았는지는 확정하지 못했다. 근거는 "받침대 콜라이더를 끄면 통과한다"는 것이다. 팔의 루트는 `ArmDriveSetup`의 `Fix Root`로 고정되어 있어서 받침대는 지지에 필요하지 않은 장식이다.

**해결**: 받침대 크기를 줄여서 뚜껑을 쥐고 들어 올리는 데까지 진행했다(확정). 영구 조치로 받침대 콜라이더 제거를 검토 중이다(미반영).

## 8. 문제: 그리퍼 열림이 끝나기 전에 후퇴함 (뚜껑을 박스에 놓은 뒤)

**증상**: 뚜껑을 박스에 놓은 뒤 후퇴 단계에서 끝점이 목표보다 18mm 낮게 멈추고 실패.

**원인 (확정, 코드 원인)**: 그리퍼를 연 뒤 0.3초만 기다리고 후퇴했는데 열리는 데는 0.8초(`JointGripper._travelSeconds`)가 걸린다. 손가락이 아직 뚜껑을 누르는 채로 올라가서 걸리거나 뚜껑이 딸려 올라간다.

**해결**: `IGripper.Opening`이 0.99 이상이 될 때까지(최대 `graspTimeoutSeconds`) 기다린 뒤 0.3초 더 안정시키고 후퇴한다. 후퇴는 실제 끝점에서 같은 x, z로 곧게 위로 올린다. 이 수정 뒤에 뚜껑이 키트 박스 위에 놓인 상태가 되는 것을 확인했다(후퇴 단계의 개별 결과는 따로 확인하지 못했다).

## 9. 문제: 쥔 뒤 들어 올리지 못함

**증상**: "뚜껑을 들어 올리지 못했습니다". 첫 걸음 목표 y=0.92인데 실제 끝점이 목표보다 12mm **높은** 곳(y≈0.94)에 있었다. 올라가야 하는데 목표가 현재보다 아래였다.

**원인 (확정, 코드 원인)**: 하강 단계의 높이 판정이 10mm라서 목표 0.91이 아니라 0.92~0.94에서 "도달"로 처리되고, 쥐는 동안 끝점이 조금 떠올랐다. 들어 올리기는 **공칭 위치(뚜껑 중심 y=0.91)** 에서 1cm씩 위로 가게 계산해서 첫 목표가 현재 끝점보다 아래가 되었다. 팔이 내려가려다 막혀 3초 뒤 실패했다.

**해결 (확정)**: 들어 올리기와 후퇴를 `CurrentToolPosition`(실제 끝점)에서 시작하게 바꿨다. 이후 뚜껑을 들어 올려 박스 위로 옮기는 것까지 진행했다.

## 10. 진단 도구가 만든 부수 문제

| 문제 | 원인 | 해결 |
|---|---|---|
| 콘솔에서 관절 표와 패드 값이 한 줄로 이어져 나옴 | 문자열의 `\n`이 파일에 들어가지 않았다(스크립트로 파일을 고치는 과정에서 이스케이프가 사라짐) | `\n`을 넣어 다시 작성하고 `grep`으로 확인 |
| `ArticulationBody does not contain a definition for 'xMotion'` (컴파일 오류) | 존재하지 않는 속성을 썼다 | 회전 관절의 잠금 상태는 `twistLock`으로 교체 |
| 실패 메시지에 자리표시자 `{NL}`이 그대로 들어갈 뻔함 | 보간 문자열 안에 파이썬 변수 이름이 남음 | 직접 `\n`으로 교체 |

**교훈**: 진단 출력은 한 번 돌려서 실제 모양을 눈으로 확인한다.

## 11. 진단 도구 목록 (재발 시 순서대로 사용)

| 도구 | 용도 | 언제 |
|---|---|---|
| `Tools > MediKit > Measure ArmB Reach` | 뚜껑 중심, 키트 박스 중심, 박스에 앉은 높이의 도달 여부, 뚜껑 크기와 방향 | 위치·크기를 바꾼 뒤 |
| `Tools > MediKit > Measure ArmB Gripper Gap` | 패드 사이 실제 간격, TCP 중앙 여부, 패드 높이 | 뚜껑 크기를 정하기 전, 한쪽 손가락이 걸릴 때 |
| `Tools > MediKit > Report ArmB Joint Limits` | 물리 엔진 기준 관절 한계, 현재 각도, 구동 목표 | 관절이 같은 각도에서 멈출 때 |
| `Tools > MediKit > Report ArmB Contacts` | 팔과 겹친 충돌체 | **깊이 0 접촉은 못 잡는다.** 결과를 그대로 믿지 말 것 |
| `LidCoverTask` 실패 메시지 | 패드-뚜껑 간격, 실제 끝점 대 목표 차이, 관절 현재·목표·한계 | 모든 실패 |
| `Tools > MediKit > Setup ArmB Lid Grasp` | 뚜껑에 `Rigidbody`·`Graspable`, 팔에 `LidCoverTask` 연결 | 뚜껑 프리팹을 다시 만든 뒤 |
| `Tools > MediKit > Rebuild LidSupplyTable Prefab` | 빌더 상수로 뚜껑 박스 재생성 | 크기·높이를 바꾼 뒤(이어서 위의 Setup 필요) |
| `LidCoverTask` > 우클릭 > `Run Cover (Test)` | 컨베이어 없이 한 번 실행 | 컨베이어가 `AtPacking`을 보내기 전 |

실패 원인을 가르는 순서:
1. IK 오차가 크다 → 닿지 않는 목표 (`Measure ArmB Reach`)
2. IK는 풀리는데 팔이 못 감 → 관절 표에서 차이가 큰 관절 확인
3. 차이가 큰 관절이 매번 같은 각도에서 멈춤 → 한계(`Report ArmB Joint Limits`)와 충돌(받침대 등을 끄고 시험)
4. 한쪽 패드가 뚜껑에 닿음 → `Measure ArmB Gripper Gap`과 패드-뚜껑 간격 확인

## 12. 작업 중 겪은 부수 문제

- **`ArmB .prefab` 삭제**: 초기 자리표시 팔 프리팹(`ArmB .prefab`)을 지웠는데 `Scene_Cell`이 `Shelf` 아래에 이 프리팹의 인스턴스(`ArmB ` + `Base`, 오브젝트 7개)를 계속 참조하고 있었다. 지우면 Missing Prefab이 된다. 현재 ArmB(`Cell/Packing/ArmB`)는 `PF_ArmB_UR3` 인스턴스와 일반 `Base`로 구성되어 있어서 이 프리팹을 쓰지 않는다. **`ArmB .prefab`은 git에서 복구했다.** `PF_ArmB.prefab`(빌더가 만드는 자리표시 팔)은 참조가 없어서 삭제된 채로 있다.
- **커밋 메시지**: 처음 커밋 메시지가 "뚜껑 덮기 동작 추가"였는데 실제로 확인된 것은 덮기가 아니라 뚜껑을 집어서 옮기는 것까지였다. 메시지를 고치고 본문에 덮기는 검증하지 못했다고 적었다. 이후 뚜껑을 키트 박스 위에 놓는 것까지 확인되어, 커밋 제목이 이 범위를 정확히 말하는지 다시 확인해야 한다.
- **씬 변경 공유**: 마찰·댐핑 0.1, 뚜껑 박스 재생성, 받침대 크기 축소가 모두 `Scene_Cell.unity`에 들어가 있다.

## 13. 남은 문제와 다음 확인

1. **덮기 실패(원인 미확인)**: 뚜껑이 키트 박스 위에 놓이지만 덮이지 않는다. 실패 메시지(콘솔 전체)를 확인하지 않아서 어느 단계(후퇴, 안착 판정 등)에서 어떤 이유로 실패하는지 모른다. 먼저 콘솔 메시지와 Scene 뷰로 뚜껑이 박스에 얹힌 모양(가로 어긋남, 높이, 기울어짐)을 확인한다.
2. **3초 제한**: SRS FR-10은 "목표 자세에 3초 안에 도달하지 못하면 Fault"인데 현재는 10초로 늘려서 확인했다. 각 단계 시간을 측정해 3초를 지킬 수 있는지, 아니면 SRS를 고칠지 정한다.
3. **받침대**: 콜라이더를 영구 제거할지, 크기를 줄인 상태로 둘지. `CellSceneBuilder.BuildArm`에도 반영해야 Rebuild에서 되돌아가지 않는다.
4. **끝점 처짐(7~12mm)**: 구동 강성(`Revolute Stiffness` 10000)을 올리는 근본 대책은 팀 공유 설정이라 아직 건드리지 않았다.
5. **한쪽 손가락이 2mm쯤 안쪽으로 처짐**: 패드 간격 합이 측정값보다 약 2mm 좁아지는 관찰이 있었다. 원인(손가락 관절 처짐 등)은 확정하지 못했다.
6. **컨베이어 연동**: 컨베이어가 아직 `AtPacking`을 발행하지 않아 테스트는 `Run Cover (Test)`로만 한다.
