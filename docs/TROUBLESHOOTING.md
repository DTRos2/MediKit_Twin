## 1. 주문 "적용" 뒤 팔이 A-1로 가다 Unity가 꺼진다 (PhysX 네이티브 크래시)

작업 브랜치: `feature/pw-fr5-joint-panel` (FR-03)

### 증상

- Orders (CSV) 패널에서 "적용"을 누르면 로봇암 A(FR5)가 선반 A-1로 가고, 선반 앞에서 Unity가 꺼지며 Unity Bug Reporter가 뜬다.
- 원인을 "팔이 물건과 부딪혀서"로 짐작하기 쉽지만, 아래 조사로 확인한 원인은 달랐다.

### 크래시인지 알아보는 방법

C# 예외가 아니라 Unity 안의 PhysX가 죽는 네이티브 크래시다. Console에는 아무것도 안 남고, 로그 파일에만 남는다.

- 로그: 프로젝트 `Logs/Editor-prev.log` (크래시한 직전 세션), `%LOCALAPPDATA%\Temp\Unity\Editor\Crashes\`
- 로그에서 `Crash!!!`를 찾고, 그 아래 `OUTPUTTING STACK TRACE`의 스택을 본다.

```
physx::Dy::PxsSolverStartTask::setupDescTask
physx::Dy::PxsSolverStartTask::runInternal
physx::Cm::BaseTask::run
PhysicsCommands::PhysX::Simulate
PhysicsManager::Simulate        <- FixedUpdate 중 물리 계산
```

- 크래시 직전 로그는 항상 `칸 A-1: 카메라로 물건을 확인...`이었다. 팔이 선반 앞으로 뻗는 단계다.

### 원인

FR5 팔의 `base_link` 콜라이더가 이동 베이스 ArmA의 `Base` 박스(`Cell/Robot/ArmA/Base`)에 **파묻힌 채 계속 접촉**하고 있었다.

| 항목 | 값 (월드, m) |
|---|---|
| `Base` 박스 윗면 | y = 0.7492 |
| 팔 `base_link` 콜라이더 바닥 | y = 0.7410 ~ 0.7504 |
| 겹침 | 4개 콜라이더가 8.2mm 파고듦(밀어내는 방향이 모두 위쪽). 나머지는 1.2mm 위 |

- 팔은 베이스 윗면 위에 얹혀 있어서, 의도한 구조지만 콜라이더끼리 맞닿거나 겹친다.
- 팔 루트는 고정(`immovable`)이고, `MountedBaseFollower`가 매 `Update`마다 `TeleportRoot`로 옮긴다. 베이스 박스는 Rigidbody 없이 움직인다.
- 이 접촉이 남은 채로 팔이 선반 앞까지 뻗으면 PhysX 솔버가 죽는다.
- **PhysX 안에서 정확히 왜 죽는지는 확인하지 못했다.** "이 접촉이 있으면 죽고, 없으면 안 죽는다"는 것만 실험으로 확인했다.
- 팔을 아무리 다른 각도로 움직여도 이 접촉은 안 사라진다. 루트가 베이스에 붙어 있기 때문이다.

### 조사 방법

Unity를 배치 모드로 띄워 사람이 하는 일을 대신 돌렸다. Editor 스크립트가 `Scene_Cell`을 열어 재생하고, "적용" 버튼과 같은 호출(`IOrderInput.LoadText`)로 주문을 넣은 뒤, 팔 위치를 기록했다.

```
Unity.exe -batchmode -projectPath <프로젝트> -executeMethod <Editor 스크립트>.Run -logFile <로그>
```

- 프로젝트가 에디터에 열려 있으면 "another Unity instance is running" 대화상자가 뜬다. 실험 중에는 에디터를 열지 않는다.
- 이 스크립트는 조사용 임시 파일이라 저장소에 남기지 않았다.
- 수정 전 시나리오는 5번 모두 약 10초 안에 같은 스택으로 죽어서 재현이 안정적이었다.

### 실험 결과

| 실험 | 결과 | 알게 된 것 |
|---|---|---|
| 팔 외의 콜라이더를 전부 끔 | 크래시 없음 | 접촉이 원인이다 |
| 팔 링크당 콜라이더를 1개만 남김(232개 → 10개) | 같은 자세에서 크래시 | 콜라이더 개수는 원인이 아니다 |
| `Cell/Shelf/ArmC/Base` 박스만 끔 | 첫 접근은 통과, 두 번째 시도의 쥐기 중 다른 스택(`acquireExceptionalConstraintMemory`)으로 크래시 | 이 박스 하나가 원인은 아니다 |
| 크래시 직전 접촉 스캔 | 팔과 겹친 비-팔 콜라이더는 `ArmA/Base` 하나뿐 | 범인은 이 접촉이다 |
| 팔 ↔ ArmA 콜라이더 쌍 충돌만 끔 | 60초 동안 크래시 없음 | 이 쌍이 원인이다 |

크래시 스택이 두 종류(`setupDescTask`, `acquireExceptionalConstraintMemory`)로 나왔다. 둘 다 PhysX의 접촉 처리 쪽이다.

배제한 것:
- `PhysicsGraspHolder`: 크래시는 복제 물건이 만들어지기 전, 접근 중에 났다.
- 이동 중 레이어 충돌 끄기(`LayerCollisionIgnoreScope`): `ArmBaseApproachConfig`의 레이어 이름이 비어 있어 꺼져 있다. (참고로 팔은 레이어 8, 선반은 레이어 9이고 물리 설정에서 8과 9의 충돌은 이미 무시된다.)
- 223개 "충돌 상자": 장애물 회피 계산용 수학 객체라 PhysX와 무관하다.

### 해결

`Assets/_Project/Prefabs/ArmA.prefab`의 `Base` 오브젝트 `BoxCollider`를 줄여 팔 밑동과 간격을 만들었다.

| 필드 | 전 | 후 |
|---|---|---|
| `m_Size` | `{x: 1, y: 1, z: 1}` | `{x: 1, y: 0.9072, z: 1}` |
| `m_Center` | `{x: 0, y: 0, z: 0}` | `{x: 0, y: -0.0464, z: 0}` |

- 콜라이더 윗면이 0.7492 → **0.7000**으로 약 5cm 내려갔다. 아랫면(0.2188)은 그대로다.
- 팔 콜라이더 바닥(0.7410)과의 간격은 **4.1cm**다. 접촉은 두 콜라이더의 접촉 거리 합(기본 `defaultContactOffset` 0.01 × 2 = 약 2cm)부터 생기므로, 8mm만 줄이면 모자라고 2cm보다 넉넉하게 띄워야 한다.
- 눈에 보이는 큐브(메시)는 그대로이고 콜라이더만 줄였다. 화면은 달라 보이지 않는다.
- 씬은 `Base` 콜라이더를 덮어쓰지 않아서(`Transform` 위치와 스케일만 덮어씀) 프리팹만 고치면 반영된다. 위 숫자는 씬의 `Base` 스케일(y 0.5304) 기준이다. 프리팹 단독의 `Base`는 스케일이 y 0.748이라 윗면이 약 7cm 내려간다.

### 검증

- 수정 후 샘플 주문 3건(키트 7개)으로 150초, A-1 시도 11번을 돌렸다. 크래시가 없었고 컴파일 에러도 없었다. 이 geometry 수정은 한 번 돌렸다.
- 임시로 시험한 다른 방식(팔 ↔ 플랫폼 충돌을 `Physics.IgnoreCollision`으로 끔)도 90초와 150초 두 번 통과했지만, 충돌을 끄지 않는 쪽을 택해 코드를 뺐다.

### 장애물 회피 계산과의 관계

프로젝트에는 이미 계산으로 피하는 기능이 있다(`ArmCollisionChecker`, `ArmClearanceProbe`). 팔 링크의 위치를 순기구학으로 구해 선반·박스와 겹치는지 보고, 겹치면 도구 방향이나 서는 자리를 바꿔 본다.

- 이 기능은 베이스 0.2m 안의 콜라이더를 "팔이 올라탄 베이스"로 보고 장애물에서 뺀다(`ArmPerceptionBuilder.FindMounts`). 계산에서는 받침대가 이미 장애물이 아니었고, 물리 엔진만 그걸 모르고 접촉시키고 있었다.
- 그래서 이번 접촉은 계산 회피로 못 피한다. 팔이 어떤 각도로 가도 루트의 접촉은 그대로이기 때문이다.

### 재발 방지

- 팔 밑동 콜라이더와 베이스 콜라이더의 간격을 **2cm 이상**으로 유지한다. 팔이나 베이스의 높이, 위치, 크기를 바꾸면 다시 확인한다.
- 간격은 보이는 메시를 건드리지 않고 **콜라이더만 줄여서** 만든다.
- 같은 스택으로 다시 죽으면 이 문서의 "크래시인지 알아보는 방법"부터 본다.

### 아직 해결하지 못한 것

크래시와는 별개다. 위 수정으로 해결되지 않았고 조사도 끝나지 않았다.

- **A-1 집기가 실패한다.** "도구 끝점에서 물건 중심이 0.34m 떨어져 있다"로 쥐기에 실패한다. `Config/TaughtPickPoses.json`에서 A-1 자세만 도구 위치가 `(1.89, 0.82, 2.10)`이다. 다른 칸(A-2~A-4)은 `y 0.73, z 2.27`이다. 자세를 다시 알려 줘야 할 가능성이 크다. A-1 칸 바로 아래 `Cell/Shelf/ArmC/Base` 박스와 팔이 부딪혀 자세가 밀렸을 가능성도 있는데 확인하지 못했다.
- **UR3 팔(ArmB)도 같은 구조일 수 있다.** 받침대 박스(`Cell/Packing/ArmB/Base`)와 팔 밑동 콜라이더가 겹쳐 보인다. 지금은 움직이는 베이스에 얹혀 있지 않아 실제로 터지는지는 확인하지 못했다.
- **씬의 `TestCube_ur3_with_gripper`가 바닥 없이 계속 떨어진다.** 재생 중 y가 -39000까지 내려갔다. 크래시와는 상관없는 것으로 보이지만 따로 확인하지 않았다.
- `MountedBaseFollower`는 베이스가 멈춰 있어도 매 `Update`마다 `TeleportRoot`를 부른다. 이번 크래시의 필요 조건은 아니었고(접촉만 없애면 안 죽었다) 바꾸지 않았다.

### 같은 스택으로 죽는 다른 원인

위 스택(`PxsSolverStartTask::setupDescTask`)은 PhysX의 접촉 처리 쪽 어디서든 나올 수 있어서, 같은 스택이라고 같은 원인이 아니다. 지금까지 확인된 원인은 셋이다.

| 원인 | 문서 |
|---|---|
| 팔 밑동 콜라이더가 베이스 박스에 파묻힌 채 접촉 (이 문서 1절) | 위 해결 |
| 관절 몸체(`ArticulationBody`) 링크에 `OnCollision*` 접촉 알림을 달았다 | [E2E 시험 문서의 운용 함정](troubleShooting/FR-03_E2E_시험으로_원인_좁히기_진단_도구와_운용_함정.md) |
| 물건을 쥘 때 `Physics.IgnoreCollision` 쌍을 수백 개 걸어 둔 채 다른 팔(팔 B)의 구동 값을 썼다 | [FR-10 문서](troubleShooting/FR-10_물건_든_박스에_팔_B가_뚜껑을_덮을_때_PhysX가_죽는다_충돌_무시_쌍을_많이_걸어_두면_다른_팔의_구동_쓰기에서_솔버가_죽는다.md) |

크래시가 나면 스택이 같아도 "방아쇠(그 순간 하던 일)"와 "그 전에 깔아 둔 조건"을 따로 가려야 한다. 한 가지 원인을 고쳤다고 이 스택이 다시 안 나온다고 보지 않는다.
